## 1. 用户已确认的核心场景

主要需求不是在微信中直接编辑或删除服务器文件，而是以下三类业务：

1. **微信查找和分发文件。** 员工用自然语言查询品牌、商品及相关资料，机器人找到文件后发回微信。交互应灵活，不要求用户输入服务器路径、JSON、哈希或逐次去终端审批；必要歧义再询问。
2. **资质共享群收件、识别和分类归档。** 指定群收到商品图、质检、手卡、授权等文件后，机器人取得实际原件，识别类别及关联品牌/商品，按既定目录规则放入文件系统。
3. **AI 主机使用工作副本。** Hermes 找到文件后通过文件 API 下载副本到 AI 主机，调用工具加工；加工结果再通过 API 放回文件系统。即使涉及修改，也优先走下载副本、处理、回存，而不是直接在正式文件库里改原件。

直接编辑正式文件和删除的频率低，优先级排后。此前按通用 CRUD 排列的“新建后立即开发修改、删除”不再作为当前业务推进顺序；已完成的只读、新建及审计能力继续复用，不推倒重建。

## 2. 查找与微信回传

目标链路：微信需求 → 请求人/收件会话授权 → Hermes 检索资料 → 选择文件 → 受控取得原件 → Gateway READY Artifact/Delivery → 微信实际附件及回执。

- 查询默认不逐次要求人工批准。多份相近资料时根据商品、规格、批次、适用范围等澄清，不把上传时间最新等同于业务适用。
- 检索可结合文件名、商品别名、类别和资料元数据；引用前文的自然语言交互是需求，不代表引用正文注入已完成。
- 只是分发原件时，不强制让大文件先绕到 AI 主机再传回 CFserver。选择文件与文件物化可以分离，但必须保留 Gateway 的授权、READY Artifact、投递与回执边界，不能绕开现有 D028。
- 需要发送的是微信可打开的真实附件/图片，不是 AI 主机路径或包含长期 Token 的链接。
- 默认回到原请求会话。跨群/跨联系人分发需要明确目标及授权；“查询自由”不等于跨身份自由读取。

## 3. 共享群附件归档

目标链路：指定资料群收到消息 → 确认群/发送人/文件准入 → 取得实际字节 → CFserver 受控持久化及附件登记 → 待识别任务 → Hermes 分类与商品匹配 → FileBrowser API 归档 → 完整性核验 → 状态/结果回复。

原件收妥与 AI 分类应分开。AI 主机离线时，目标是由 CFserver 保留已成功取得的原件和待处理任务，开机后再分类；这尚需实现和离线验收，不承诺当前微信离线期间所有历史附件都能补拉。临时收件区不是第二套正式文件服务，需有生命周期、失败恢复及引用追踪。

### 分类和目录

类别包括商品图、质检、手卡、授权；结合文件名、实际内容及消息说明判断，不能仅按扩展名归类。原生文档优先提取可用文字，扫描件/图片使用已有适用能力；不因此新建独立 OCR 系统，保持 D006。

商品图应区分商品/规格和用途；质检关联商品、批次或报告编号；手卡关联商品及版本；授权关联授权范围和文件写明的有效期。未写明或看不清的字段留空/待确认。分类成功不等于证明质检报告或授权文件真实、有效或适用于所有商品。

目录采用受控模板，而非模型自由创建任意路径。具体业务目录、品牌/商品字典、群标识、发送人白名单及自动归档阈值尚待确认，不在此假定已经配置。品牌级文件可保存一份原件、关联多个商品，避免无意义复制。

### 自动执行与例外

- 预授权群/发送人、已确定规则、目标范围内的新增且不覆盖：目标是自动归档，不逐个要求 PowerShell 批准。
- 类别/商品不确定、信息冲突或规则不覆盖：先保存为待确认，询问或排入人工队列，不丢原件、不乱放。
- 保留来源消息、发送者、接收时间、原文件名、摘要及分类依据的受限记录；不把这些真实数据提交 Git。
- 同一消息重收不重复创建；相同字节再次出现可增加来源关联；同名不同内容不能静默覆盖。
- “看到附件元数据”“原件已收妥”“分类完成”“正式归档”“结果已发送”分别记录，不能用一句“已保存”混淆。

当前普通群未 @ 不调用 AI 的规则不全局关闭。指定资料群后台收件应通过独立、明确的入站策略接入；收件权限不等于允许所有群消息进入模型，也不启用 group_shared 或共享全部成员上下文。

## 4. AI 主机加工与回存

目标链路：Hermes 找到正式文件 → API 下载至任务专属 input → work 中加工 → output 产物检查 → API 上传新文件/新版 → 记录原件关联 → 按需要从微信分发。

- 文件系统保存正式原件与产物，Windows 保存工作副本和中间文件。不得让 Gateway/Hermes 挂载正式存储或数据库绕过 FileBrowser API。
- 默认另存新文件或新版本，保留原件；现有系统是否有完整版本管理需单独验证，不能仅凭另存功能宣称版本管理已交付。
- 明确要求替换正式版本时，需检查处理期间原件是否变化、结果完整性及回滚/保留策略；客户端先读哈希再写不等于服务端原子条件写。
- 质检、授权等原始凭证保持原件，转换或加工结果标明派生关系，不冒充原始凭证。
- 本地工作目录按任务隔离、有限保留。正式回存未成功前不得清理唯一产物；过期/失败工作需可追踪恢复。

## 5. 职责和升级边界

- `CF_agent-wechat`：微信收发与上游附件能力适配，不做文件业务理解。
- `CF_agent-gateway`：身份/会话准入、附件引用及生命周期、持久任务和投递状态、恢复与审计关联；分类和内容加工放独立模块/Skills，不塞入核心。
- Hermes/文件业务模块：检索、分类、商品匹配、调用处理工具、工作副本和产物流程；不能由模型自行扩权。
- `CF_filebrowser-enterprise`：唯一正式文件 API、存储授权和持久审计。
- Hermes 插件是可替换接入层，不锁死某个 Hermes 提交，不要求升级 Agent 就重部署 FileBrowser或重签文件凭据。升级仍要验证实际接口与工具兼容。

## 8. 后续资料与 Skill 试点

可以安排小批量资料整理与首批文件类 Skill，不必等 ERP 自动化、全部部署工作、新 RAG 或自研 Skills Runtime。商品资料查询/图包交付、素材归档、资料完整性检查为首批方向；复用现有受限查询/文件操作/商品素材工具、摘要与清单基础。

商品字典、选件与目录模板、来源/冲突/去重/待确认、必备资料与完整性规则仍须细化；多商品、多身份、真实模型选工具、群准入、离线续接和异常处理需独立现场验收。详见[试点基础与缺口表](../status/current-progress.md#首批文件类-skill-的可用基础与缺口)。这是后续安排，不是已经交付或工期承诺。

当前正式机器仍使用项目插件和客户端；最终要求电脑仅安装官方 Hermes 并配置少量参数，服务端一条正式可复用入口。禁止把手工复制插件、额外 EXE/常驻进程或依赖工作树/旧回执当最终交付。简部署候选由独立 Gateway 任务开发验证中，MCP 仅为验证路线，详见[部署目标](../deployment/deployment-guide.md#最终部署标准与候选边界)。

项目最后安排群聊会话及多人/连续消息交互、AI 面向当前场景/问题/任务主动检索获准的完整聊天档案、Gateway 向获准人员/群聊群发消息及附件。档案不限 Hermes 自身历史或成功任务，授权档案完整不等于手机微信全历史已采集。Gateway Web 仍是后续规划，本轮仅记需求。
