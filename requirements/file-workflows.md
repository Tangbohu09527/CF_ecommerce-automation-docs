## 1. 用户已确认的核心场景

四仓当前先保证消息、权限、会话/Profile 路由、文件取得与操作、原名和结果通道等平台基础。商品理解与业务流程由 Hermes 和后续 Skills 承担，不继续拆成四仓必须逐项开发的业务系统。当前文件触发以以下三种行为区分：

1. **普通收件。** 私聊/群聊没有安排任务时，一般不主动处理、不回复，不自动下载全部附件并永久归档；聊天消息与附件元数据留档继续保留。
2. **按任务取得。** 员工明确要求查看或处理时，取得必要原件交给 Hermes；任务临时取得不等于正式文件库保存。
3. **按要求保存。** 员工明确说“存起来”才通过文件服务保存到对应目录。指定纯文档群可以明确配置自动收件/保存，这是例外，不扩展为全部群聊规则。

已有查询、复制、移动、改名、替换、可恢复删除/还原和素材打包回传基础继续保留，不为穷举自然语言表达无限扩展开发和测试。明确的权限、群接入、通道或文件名缺口仍是基础问题，不能降为提示词优化。完整职责与文件触发规则见[权威需求](./confirmed-platform-scope.md)。

## 2. 查找与微信回传

目标链路：微信需求 → 请求人/收件会话授权 → Hermes 检索资料 → 选择文件 → 受控取得原件 → Gateway READY Artifact/Delivery → 微信实际附件及回执。

- 查询默认不逐次要求人工批准。多份相近资料时根据商品、规格、批次、适用范围等澄清，不把上传时间最新等同于业务适用。
- 员工明确提出商品/文件需求后，Hermes 检索唯一正式文件系统；不能确定选哪个时直接询问员工。商品别名、手卡匹配、目录分类、字段与模板填充由 Hermes 和后续 Skills 理解，不在 Gateway 硬编码业务字典或排版引擎。
- 常见群手卡场景为获准员工在群内 @ Bot，读取当前群相关近几条消息，确定商品后检索并回到原群；当前群必要上下文属于平台基础，不与后置跨会话完整档案智能检索混同。引用正文实际接入仍须单独核验。
- 只是分发原件时，不强制让大文件先绕到 AI 主机再传回 CFserver。选择文件与文件物化可以分离，但必须保留 Gateway 的授权、READY Artifact、投递与回执边界，不能绕开现有 D028。
- 需要发送的是微信可打开的真实附件/图片，不是 AI 主机路径或包含长期 Token 的链接。
- 默认回到原请求会话。跨群/跨联系人分发需要明确目标及授权；“查询自由”不等于跨身份自由读取。

## 3. 明确保存与指定纯文档群例外

目标链路：员工明确要求保存，或命中已配置的纯文档群保存规则 → 检查员工/群使用权限及文件权限 → 按任务取得实际字节 → Hermes 按明确业务规则选择目录，歧义询问 → FileBrowser API 保存 → 完整性核验与状态记录 → 按任务要求回复。

聊天消息/附件元数据留档、任务临时取得原件、正式文件库归档是三个独立动作，不能强制绑定。临时收件区不是第二套正式文件服务；已取得文件、任务状态和聊天档案仍需持久保存及防重复。D005 持久化原则保留。

2026-09-27 安排的“AI 主机离线时 CFserver 先收所有原件，开机后补分类”已由本轮决定移出当前必做范围，不再安排该专项。离线请求如何提示、结束或保留待处理尚待细化，不能默认第二天自动执行全部积压业务。

### 分类和目录

商品图、质检、手卡、授权的具体分类是后续 Hermes/Skills 业务规则，不列为当前四仓逐项实现的分类系统。不能仅按扩展名归类；原生文档优先使用可用文字，扫描件/图片使用已有适用能力，不新建独立 OCR 系统，保持 D006。

商品图应区分商品/规格和用途；质检关联商品、批次或报告编号；手卡关联商品及版本；授权关联授权范围和文件写明的有效期。未写明或看不清的字段留空/待确认。分类成功不等于证明质检报告或授权文件真实、有效或适用于所有商品。

目录必须在文件服务授权范围内；具体业务目录、品牌/商品字典和纯文档群规则后续细化，不假定已经配置。品牌级文件的一份原件关联多商品仅是建议，不能替用户预设共享或复制策略。

### 自动执行与例外

- 只有明确配置的纯文档群保存规则允许自动收件/保存；其他会话按员工当前任务取得，明确要求保存后正式归档，不逐个要求 PowerShell 批准。
- 类别/商品不确定、信息冲突或规则不覆盖：直接询问；已经按任务取得的必要原件保留可追踪状态，不将“待确认”擅自变成正式归档或猜测目录。
- 保留来源消息、发送者、接收时间、原文件名、摘要及分类依据的受限记录；不把这些真实数据提交 Git。
- 同一消息重收不重复创建；相同字节再次出现可增加来源关联；同名不同内容不能静默覆盖。
- “看到附件元数据”“原件已收妥”“分类完成”“正式归档”“结果已发送”分别记录，不能用一句“已保存”混淆。

普通群未 @ 不执行 AI 与持续留档是不同要求。指定纯文档群例外需要明确入站策略；群内只有获准员工能发起任务，其他参与者可作为获准任务上下文但不自动获得 Bot 权限。按 B 方案每群独立 Profile/持续群会话是已确认目标，现有 `group_sender` 等实现不能自动当作目标已经完成。

## 4. AI 主机加工与回存

目标链路：Hermes 找到正式文件 → API 下载至任务专属 input → work 中加工 → output 产物检查 → API 上传新文件/新版 → 记录原件关联 → 按需要从微信分发。

- 文件系统保存正式原件与产物，Windows 保存工作副本和中间文件。不得让 Gateway/Hermes 挂载正式存储或数据库绕过 FileBrowser API。
- 取得群内指定模板和企业手卡内容后，由 Hermes 完成内容修改，平台提供输入、文件访问与结果通道；不要求四仓开发模板排版引擎。没有明确要求，不覆盖正式原件，也不自动归档派生稿。明确要求回存时默认另存新文件/新版并保留原件；完整版本管理仍须单独验证。
- 明确要求替换正式版本时，需检查处理期间原件是否变化、结果完整性及回滚/保留策略；客户端先读哈希再写不等于服务端原子条件写。
- 质检、授权等原始凭证保持原件，转换或加工结果标明派生关系，不冒充原始凭证。
- 本地工作目录按任务隔离、有限保留。正式回存未成功前不得清理唯一产物；过期/失败工作需可追踪恢复。

## 5. 职责和升级边界

- `CF_agent-wechat`：微信收发与上游附件能力适配，不做文件业务理解。
- `CF_agent-gateway`：身份/会话准入、附件引用及生命周期、持久任务和投递状态、恢复与审计关联；分类和内容加工放独立模块/Skills，不塞入核心。
- Hermes/后续 Skills：检索、分类、商品匹配、模板/字段/提示词与电商业务流程；不能由模型自行扩权。Skills 等四仓基础任务完成后，由用户找 Hermes 制作并单独建立仓库；本轮不建仓、不制 Skill、不建设新 Runtime/RAG。
- `CF_filebrowser-enterprise`：唯一正式文件 API、存储授权和持久审计。
- Hermes 插件是可替换接入层，不锁死某个 Hermes 提交，不要求升级 Agent 就重部署 FileBrowser或重签文件凭据。升级仍要验证实际接口与工具兼容。

## 8. 后续 Skills、部署与群聊范围

原“现在并行安排首批文件类 Skill 试点”是本轮已调整的历史安排。当前先完成四仓平台基础，之后由用户找 Hermes 制作 Skills 并单独建立 Skills 仓库；商品资料查询、素材归档与完整性规则可以复用已有工具，但本轮不安排试点或新 Runtime/RAG。

商品字典、选件与目录模板、资料完整性等业务规则后续由 Hermes/Skills 承接；明确权限、群准入、输入/结果通道和原文件名缺口仍由平台解决。已有代码、隔离测试、真实模型选工具和现场实收分别记状态，不因为工具存在宣称业务规则已交付。

最后现场记录中的正式机器仍使用项目插件和客户端；最终要求电脑仅安装官方 Hermes 并配置少量参数，服务端一条正式可复用入口。禁止把手工复制插件、额外 EXE/专用常驻客户端或源码修改当默认前提。简部署与恢复入口保留最终要求但优先级后移；PR23/PR24 等已有候选和最终证据保留，MCP 仅为候选路线，详见[部署目标](../deployment/deployment-guide.md#最终部署标准与候选边界)。本轮不继续部署研发。

每群独立 Profile/持续群会话、执行中补充与当前群必要上下文是当前平台基础需求；不可因旧“群聊最后做”一并排除。群发及高级跨会话完整档案智能检索继续后置。持续聊天采集、Web 按会话/人员/时间查看和机器人受控查询日期范围见[权威需求](./confirmed-platform-scope.md)，不把轮询当历史查询，也不承诺 Bot 在线就已全量留档。
