## 2. 权限分组与B方案

**用户已确认：** 先判断员工微信是否获准使用 Bot，再判断该员工是否获准在群聊使用 Bot。开通权限与分组是两件事；新员工可以处于“已授权、未分组”，此时不暗中分配默认 Profile、不自动创建档案。群指令和 `@` 的发起者也须是获准员工；其他参与者的发言可作为获准任务的相关上下文，不因此获得使用权限。

Gateway Web 后续支持员工分组和微信群分组，按部门、岗位或业务设定，不预设组数、人数或电脑数。私聊按员工所属组选择模板；群聊按该群所属组选择模板，同时核验发起员工权限。换模板分组不自动提升文件权限。

配置档案是 Hermes 界面中的真实 **Profile**，包含独立配置、`SOUL.md`、Skills 及相应会话/记忆状态，不是 Gateway 提示词片段，也不是普通会话 ID。明确采用 **B 方案：分组是模板，Profile 按员工/群独立**。

| 关系示例（仅示意） | 模板 | 独立派生 Profile | 状态边界 |
| --- | --- | --- | --- |
| 员工甲、员工乙同属客服组 | 客服组模板 | 员工甲 Profile、员工乙 Profile | 同组也不共享具体 Profile、会话或记忆状态 |
| 群 A、群 B 同属资料群组 | 资料群模板 | 群 A Profile、群 B Profile | 同组多个群也不共享具体 Profile 状态 |

独立 Profile 不等于操作系统安全沙盒；正式文件权限仍由 File Service 服务端执行，不能依据 Profile 名称、分组、前端按钮或模型自觉授权。旧 `group_sender` 按发送者隔离的实现与本轮“每群独立 Profile/群会话”的目标不是同一语义；旧记录保留，迁移与权限验证未完成前不能宣称 B 方案已接通。

## 3. Profile管理目标与验证边界

**用户已确认、待技术验证：** Gateway Web 管理分组模板；Gateway 根据模板、员工或群、目标电脑，受控确保对应真实 Hermes Profile 存在并路由消息；修改模板后同步更新派生 Profile。优先复用官方管理能力，具体接口与限制、CF 是否能接通均须验证。D026 原“Gateway 只引用、Hermes 自行管理”的历史边界由新决定调整为计划受控编排，不伪称旧实现已经满足。

| 必须分开的五层 | 当前判断口径 |
| --- | --- |
| 保存 `external_profile_ref` 及版本 | Gateway 元数据基础；存在字段不证明外部对象存在 |
| 请求实际进入对应 Hermes Profile | 请求携带字段不等于 Hermes 已采用该 Profile，须验证真实路由 |
| 自动创建 Profile | 须验证官方能力、目标电脑权限和幂等创建；现有引用模型不证明已实现 |
| 修改并持续同步 Profile | 首次克隆不等于长期自动同步，须有版本、结果和失败状态 |
| 已有会话采用新配置 | 须验证新轮次、重载或其他生效条件，不能由新请求配置推断旧会话已更新 |

创建可以在分组配置生效或首次使用时触发，具体方式待验证，不预先定死。模板同步仅覆盖管理员明确管理的字段；不得覆盖员工/群聊天历史、已产生记忆、运行状态或独立凭据。Skills 来源和版本由后续独立 Skills 仓库决定，本轮不设计全量复制策略。模板版本、派生版本、同步结果、失败状态、生效时机须可见。

模板字段范围、调组后旧 Profile/会话和记忆的保留或迁移规则均待细化；不默认全部清空、共享或迁移。

## 4. 会话续接与执行中补充

**用户已确认：** Profile 建立后，同一私聊首次创建对应会话，后续持续使用；同一群首次创建对应群会话，后续持续使用。每条消息、文件或任务都不应创建新 Profile/会话。明确新开、重置或变更分组的规则另行细化，不默默丢历史或重做在途任务。

执行期间到达的当前任务补充指令，应能进入对应正在执行过程，不能一律等前项结束后作为无关新任务处理。须区分当前任务补充、同会话独立新请求、已结束或不可撤销动作后才收到的修改要求；后者不承诺逆转已发生的结果。

具体识别方式、官方运行中补充机制与 API 接法待技术实现，不预先发明复杂合批系统。Gateway 同线程 FIFO 和已有会话续接不是“执行中补充已完成”；Hermes 桌面/CLI 的行为也不是 CF API 接入已验证。

## 5. 文件触发与业务职责

**用户已确认：** 普通私聊/群收到文件，没有安排任务时一般不主动处理、不回复，不自动下载全部附件并永久归档。员工明确要求查看/处理时，按任务取得必要原件并交给 Hermes；明确说“存起来”时，经 File Service 保存到对应目录。纯文档群可明确配置自动收件/保存，这是指定例外，不扩展到所有群。

| 动作 | 目的与边界 |
| --- | --- |
| 聊天消息/附件元数据留档 | 保存可查询的消息事实，不代表原件已下载或正式入库 |
| 任务临时取得原件 | 取得执行所需字节，经受控中转交给 Hermes；不是永久归档 |
| 正式文件库归档 | 员工明确要求或指定资料群已配置时，通过唯一正式 File Service 保存 |

员工提出商品/文件需求 → 正确 Hermes 与会话 → 通过获准工具检索唯一正式文件系统 → 正确文件回到获准微信会话。无法确定就询问员工。查询、复制、移动、改名、替换、可恢复删除/还原、商品素材打包及回传等已有基础保留，不为穷举自然语言说法无限扩开发和测试。

常见手卡场景是获准员工在群中 `@`，机器人取得当前群相关近几条消息，理解商品需求、检索手卡、发回原群。较少见模板场景是按任务取得群内指定模板与企业手卡，由 Hermes 修改，平台负责输入、文件访问和结果通道；四仓不开发模板排版引擎。不经明确要求，不覆盖正式原件、不自动归档派生稿。别名、手卡匹配、分类细节与模板业务由 Hermes 理解、记忆和后续 Skills 承担，不硬编码到 Gateway。

合法原文件名正确保留是平台基础必修项，不能擅加无意义前缀或替换中文后交给员工。已有修复候选和隔离验证保留，但实际协议部署与原名收件验收未完成，不降级为提示词或可忽略的体验问题。

PDF/PNG 原样回传保留为通道证据，不等于“按要求保存、以后独立检索交付”全部完成。D041 的 PNG 业务结果继续接受，不再追查原 PNG 字节差异；ZIP 入站失败/缺验收、正常 ZIP 出站及原名缺口分别保留。

撤出当前必做的“AI 主机关机后 CFserver 收所有原件、开机自动分类补业务”专项。D005 的聊天档案、已取得原件、任务状态持久化与防重复继续成立。离线请求如何提示、结束或保留待处理尚待细化，不默认第二天执行全部积压业务。

## 6. 聊天档案与日期查询

**用户已确认：** Bot 在服务端在线期间，私聊和群聊消息持续采集留档。同一份 Gateway 消息档案供人工 Web 按会话/人员/时间查看，也供机器人按获准指令读取相关上下文或日期范围。

轮询是采集机制，不是历史查询接口；已归档的某天/某月记录直接查档案，不重新轮询微信历史。采集不等于触发 AI，未 `@` 可留档而不执行；普通文件不主动处理不等于聊天消息不保存。保留现有 Message、时间字段、读取及管理 API 基础，不推倒消息库。

当前缺口须并列：self 消息在 Poll 中跳过；Gateway 自身出站另有 Response/Delivery；Bot 账号从其他来源自发的消息并不因此全部进入 Message。Poll 停止、采集范围、上游窗口和连续性问题都会影响完整性，所以“Bot 在线”不等于“全部消息已存好”，页面未做也不是唯一缺口。防回环应阻止自发消息触发 AI，而非永久禁止归档。

| 时间字段 | 含义 |
| --- | --- |
| `occurred_at` / 上游 `timestamp` | 消息实际发生时间及其规范化值；当前管理查询主要按该时间与起止条件筛选 |
| `received_at` | 接入层收到/接收消息的时间，不替代消息发生时间 |
| `created_at` | 数据库记录创建时间，不等于微信发言时间 |

北京时间“某天/某月”先转成明确起止区间和时区语义。目标按分页完整读取实际已归档且获准的记录，边界条件/时区映射需准确实现；不等于全部记录一次塞入模型。机器人访问须有受控工具和权限，不能给模型管理员 Token 或数据库访问权限。

当前会话近几条消息、明确引用和明确日期范围查询是当前平台基础使用需求；后置的是更高级跨会话完整档案智能检索，不能据此把当前群取上文一律拖到最后。

**用户已确认方向，尚未开发页面：**

1. 员工 Bot 使用权限与群聊使用权限。
2. 员工分组、微信群分组。
3. 分组 Profile 模板与 B 方案派生 Profile：目标电脑、版本、创建/同步结果及失败状态。

5. 已采集私聊/群聊记录，按会话、人员和时间查询。
6. 可接任务的 AI 电脑、运行/排队任务及实际资源信息。
7. 员工/群/分组使用频率，帮助分配电脑。

各项已有数据库/读取 API、缺管理写接口、缺数据采集、未有页面要逐项列明，见[当前状态矩阵](../status/current-status.md)。不能笼统称后台全做好只差 Web。增删员工权限的正常目标是 Web 管理便利操作，不继续将一串 SSH/SQL 手工步骤设计为常规流程；权限始终由服务端执行。

电脑数量由实际人数、使用频率与资源需要决定，不预设一、二或三台。用户在 Web 按部门/岗位/业务分组，明确将分组任务分配给电脑，对应每员工/群的独立 Profile 在目标电脑上运行。当前方向是可观察、可手工配置的组到电脑分配，不强制 UI 必须另一台、非 UI 必须主机。

CPU/内存监控和使用频率为后续方向；自动阈值分流、复杂负载均衡、执行中迁移不是已确认必做。不代定阈值或算法。已有会话/任务与电脑映射须明确，改变分配不能默认丢历史、重复执行或无声切换；生效规则待细化。

## 8. 后置范围部署与恢复

**用户已确认：** 简部署、统一恢复入口保留最终要求，优先级后移；纯配置 MCP 改造和新机安装不再是当前唯一主线。不回滚、不废弃已存在候选，也不因本轮同步继续部署研发。

恢复目标是故障/断电后开机运行一个入口，检查并恢复缺失服务；微信在线保留现有登录，离线再提示扫码；分别确认服务与收发状态并给出明确结果。不默认清 runtime、重装、升级、迁移或每次强制 fresh QR，不盲重做结果不明的历史任务。旧 D032 forced-QR 契约与此目标有冲突，当前运行脚本仍执行旧契约，须后续受控调整与验证；本轮不修改脚本。无人值守 HA、自动故障切换和完整 watchdog 不捆绑为当前交付条件。

最终仍要求服务端一句话部署加必要参数；电脑安装官方 Hermes，两边少量配置即可使用，插件尽量不要有。D040 保持：不将额外项目 EXE、专用常驻客户端、手工复制插件或修改官方源码作为未经批准的默认前提。有技术限制先验证并报告。

PR23/PR24 及相关组件候选和失败/成功证据完整保留：官方完整默认依赖与远程图文/合成 ZIP 实验不等于纯配置可信任务关联和授权返回链已通；统一三组件入口的容器隔离成功不等于真实新机、booted systemd 或整机重启通过。详见[部署指南](../deployment/deployment-guide.md)和[PR12 固定证据](../validation/records/2026-10-20-configuration-only-candidate.md)。

业务 Skills 与 ERP/平台操作后续独立安排；群发、高级跨会话完整档案智能检索继续后置。“每群独立 Profile/会话”、当前群必要上下文和执行中补充属于当前平台基础，不再被旧 D043 的“群聊全部最后做”覆盖。
